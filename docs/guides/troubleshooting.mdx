# Troubleshooting

Diagnostic procedures and solutions for common deployment, configuration, and runtime issues.

## Controller diagnostics

### Preflight checks with `raft doctor`

Run `raft doctor` on your controller to inspect host health across configured locations:

```sh title="CONTROLLER: Run environment health check"
raft doctor
```

`raft doctor` connects to each host over SSH and reports:
- Incus version running in project `raft`
- Compatibility of the installed expiry worker with the CLI
- Active status of host systemd services (`incus`, `raft-expire.timer`, `raft-network.service`)
- Host root filesystem disk usage (`df -h /`)
- Status and usage of the shared `raft-data` Btrfs pool, and of the `raft-disks` LVM thin pool when own box disks are enabled (otherwise `own box disks: not enabled (redeploy with --disk-pool SIZE)`)
- Count of existing saved containers

<Callout type="info" title="Doctor scope">
`raft doctor` reports runtime daemon, expiry-worker compatibility, and storage status. It does not validate image fingerprints, inspect nftables bridge rules, or emit 5 GiB low-disk warnings. A host without `raft-disks` is healthy: own box disks are opt-in.
</Callout>

### Expiry worker differs from the CLI

An active expiration timer can still run an older worker. Installing or updating
the controller CLI does not deploy host code. `doctor` checks the same worker
protocol as disposable creation and retention cleanup, without running expiry or
changing any boxes. It exits nonzero and names the location on a mismatch.

Review the host deployment changes, then deploy from the checkout matching your
CLI. Replace `lab` with the location reported by the diagnostic:

```sh title="CONTROLLER: Explicitly update a reviewed host deployment"
python3 deploy/deploy.py --location lab
raft doctor
```

Deployment updates host infrastructure as well as the expiry worker. Do not run
it on a shared host without authorization. Do not remove the compatibility check
or mark an old worker as current; older workers may retain expired disposable
boxes instead of deleting them.

### Listing active and stopped containers

Inspect workspace states across locations:

```sh title="CONTROLLER: List workspaces across all hosts"
raft list

# Filter by a single location
raft list --location lab
```

If a host is unreachable over SSH, the CLI reports a connection failure. An unreachable host does not mean containers are absent or deleted.

## Host-side diagnostics

Connect to the host over SSH to inspect underlying services when commands fail.

### Inspecting Incus project status

Verify container states and storage pools in project `raft`:

```sh title="HOST: Inspect containers and storage pools"
sudo incus --project raft list
sudo incus --project raft storage info raft-data
```

### Checking host systemd units

Raft installs two systemd units on the host:
- `raft-network.service`: Applies firewall and bridge isolation rules before Incus starts.
- `raft-expire.timer` / `raft-expire.service`: Runs the expiration worker every 15 seconds to stop expired workspaces.

Inspect unit logs with `journalctl`:

```sh title="HOST: Check Raft systemd unit logs"
sudo systemctl status raft-network.service
sudo systemctl status raft-expire.timer
sudo journalctl -u raft-expire.service -n 50 --no-pager
```

<Callout type="warn" title="Host journals and guest secrets">
Host system journals can capture command lines, arguments, and environment variables executed in guest containers. Treat host logs as sensitive records that may contain guest credentials.
</Callout>

### Manually triggering garbage collection

The host timer enforces expiry every 15 seconds. Trigger an immediate expiration run from the controller:

```sh title="CONTROLLER: Run expiration workers manually"
raft gc
```

Expired persistent containers transition from `Running` to `Stopped` and retain
files and snapshots. Expired disposable containers are deleted, including their
snapshots. Use `raft gc --location lab` to check only one host. The timer normally
checks every 15 seconds; host outages, graceful shutdown and long locked
operations can delay expiry. See [Lifetime and persistent services](./long-running-services.mdx).

## Common error scenarios

### Configuration errors

#### Missing configuration file error
If `~/.config/raft/incus.json` does not exist, the CLI raises `FileNotFoundError`. Create the configuration directory and file. Set mode `0600` on the file only.

#### "Configure at least one host in ~/.config/raft/incus.json"
The configuration file contains valid JSON that is `{}` or is not an object (an empty file raises a JSON decoding error instead). Ensure the file defines at least one location with a non-empty `ssh` string.

#### "Build an image and configure its full immutable fingerprint before creating boxes"
The `image` field is missing or is not a 64-character hexadecimal SHA-256 fingerprint. Supply the full fingerprint from `sudo incus --project raft image list raft-dev --format json`.

### Sizing and disk errors

Raft has no box count limit and no size budget. These errors come from the
request itself or from the host:

#### "Requested N CPUs, but this host has M" or "Requested SIZE RAM, but this host has N GiB"
The request is larger than the whole host. Ask for at most the host's CPUs and RAM; `raft capacity` shows both.

#### "LOCATION has no raft-disks pool, so own box disks are not enabled there"
Own box disks are opt-in and this host was deployed without them. Nothing was created. Enable them with `python3 deploy/deploy.py --location <location> --disk-pool SIZE`, which needs SIZE plus 20 GiB free on the host, or create the box without `--disk`. Boxes without `--disk` keep working meanwhile.

#### "own box disks would need N GiB more of raft-disks"
Each own disk, each snapshot of one, and the cached image reserve their full size in `raft-disks`, so Raft refused the request before creating anything. Destroy own-disk boxes or snapshots you no longer need, choose a smaller `--disk`, or use the shared pool. `raft capacity` shows the unreserved space. See [Reservation accounting](../reference/capacity.mdx#reservation-accounting).

#### "No space left on device" inside an own-disk box
The box filled its own disk. Delete files or Docker data inside the box, or snapshot it and create a larger copy with `raft new --from "$box/<snapshot>" --disk <larger size>`.

#### Low disk warnings
`raft capacity` warns when free space on host disk or the `raft-data` pool falls below 5 GiB. This warning is diagnostic and does not halt container operations. Clean up dangling images, old snapshots, or unused containers to free space.

### Network and forwarding issues

#### Port forward connects but returns connection refused
Verify that the guest service binds to `0.0.0.0` or the container's `eth0` IP address. Services bound strictly to `127.0.0.1` inside the container cannot receive traffic routed through the bridge.

#### Workspaces cannot reach other workspaces on the same host
This is intended behavior. Raft configures nftables bridge filtering on `rfbr0` to prevent communication between workspaces on the same bridge.

### Host crash during recovery

If the controller crashes or SSH drops while `raft recover` is transferring an archive:
1. Check the `Recovery handle: <location>:<name>` output printed to stderr when `raft recover` started.
2. Inspect the reported handle with `raft list --location <location>` and confirm container status before removing staging.
3. Identify the exact staging file (`/tmp/raft-recovery.XXXXXXXX`) on the host by owner and timestamp.
4. After confirming container status, remove only that owned file:
   ```sh title="HOST: Remove verified owned staging file"
   sudo -n rm -f -- /tmp/raft-recovery.XXXXXXXX
   ```

<Callout type="warn" title="Do not delete by wildcard">
Never run `rm /tmp/raft-recovery.*`. It can delete files from another recovery.
</Callout>
